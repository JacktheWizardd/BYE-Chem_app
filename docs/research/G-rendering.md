# G. Rendering simulations in 2D and 3D (BYE Chem)

## 2. Notes

### 3D
- **What the engine already does** (`/Users/thewizardd/Documents/Project/BYE-Math_engine/src/native3d/`): `ByeFigure3D.tsx` mounts an `expo-gl` `GLView`, builds a three.js scene once per figure (`createGLScene`), then calls `scene.render(camera, ms)` in an effect whenever camera or time state changes; one-finger drag orbits via `PanResponder`; labels are an SVG overlay (`overlay3d` + `SceneSvg`) at projected positions. `glRenderer.ts` creates `THREE.WebGLRenderer` on the expo-gl context with a fake canvas, temporarily hides `globalThis.WebGLRenderingContext` (three >= r163 rejects it) and calls `gl.endFrameEXP()` after each render. It uses `MeshLambertMaterial`, `Line2`/`LineMaterial` for thick lines, `SphereGeometry` for dots (one mesh per dot, no instancing).
- **expo-gl facts** from the [SDK 58 page](https://docs.expo.dev/versions/v58.0.0/sdk/gl-view/): the context resembles WebGL2; about 20 WebGL2 methods are not implemented (e.g. `getUniform()`, `fenceSync()`); some old Android devices lack WebGL2; Expo recommends `expo-three` but other libraries work with workarounds; Reanimated worklet use needs `enableExperimentalWorkletSupport` (so GL calls from a worklet are possible but flagged experimental).
- **R3F caveat**: its docs say to test on a physical iOS 16+ device because simulators often have unreliable OpenGL ES support ([install](https://r3f.docs.pmnd.rs/getting-started/installation)). Our own engine already runs, but expect simulator flakiness for GL (our memory file says we test on the simulator).
- **Instancing for many spheres**: three's `InstancedMesh` draws N spheres in one draw call; it needs WebGL2 instanced drawing, which expo-gl advertises as WebGL2-like, but I found no source that confirms `drawElementsInstanced` works in expo-gl. **UNVERIFIED**: must be tested on device. A fallback that needs no instancing: `THREE.Points` with a sphere-impostor shader, or merge into one `BufferGeometry` and update positions per frame. For hundreds of atoms/particles even individual meshes are likely fine (draw-call count, not triangles, is the limit), but that is my estimate, not a measured figure.
- **Filament**: native Metal/OpenGL/Vulkan, very fast, but needs native build, worklets-core, glb assets, no web ([README](https://github.com/margelo/react-native-filament)). Would split us into two renderers (native vs web). It says "Supports old and new arch."
- **Babylon RN**: tested on RN 0.81.6 and Babylon >= 9.0.0; no Expo support promised ([README](https://github.com/BabylonJS/BabylonReactNative)).
- **react-native-wgpu**: New Architecture only, iOS/tvOS/Android/macOS, RN >= 0.81 ([install](https://wcandillon.github.io/react-native-webgpu/docs/getting-started/installation)); v0.5.17 published 2026-07-08 ([npm](https://registry.npmjs.org/react-native-wgpu)). Pre-1.0 and a dev-build-only native module; worth revisiting only if we need GPU compute (e.g. thousands of particles). Whether Expo Go can run it: the Expo SDK 58 docs list no such module, so treat as no (**UNVERIFIED** beyond that).
- **Unity/Godot**: embedding is technically possible as a native view in a dev build, but it means a second engine, large binaries and no web build. No source read; judgement only.

### 2D
- **Skia Atlas** draws many copies of one sprite image with per-instance `RSXform` transforms, and the docs say transforms "can be animated with near-zero cost using worklets" together with Reanimated ([Atlas docs source](https://raw.githubusercontent.com/Shopify/react-native-skia/main/apps/docs/docs/shapes/atlas.md)). That is exactly "hundreds of circles": render a coloured disc once into an `SkImage`, then update an `RSXform[]` each frame. Not measured here: actual fps on a mid-range phone (**UNVERIFIED**; benchmark early).
- **react-native-svg**: every `<Circle>` is a native view/shape node; at several hundred moving circles with React state updates per frame the bridge and diffing cost is high. That is my engineering judgement; I found no primary benchmark (**UNVERIFIED**). The engine's current figures are static or time-parametrised, which is a different load.
- **Web**: Skia on web requires loading CanvasKit (WASM) per the [Expo page](https://docs.expo.dev/versions/v58.0.0/sdk/skia/); this adds a download. Plain `<canvas>` would be smaller but is a second code path.

### 3. Simulation loop off the JS thread
- **Reanimated 4.7.1** and **react-native-worklets 0.13.0** are the Expo SDK 58 versions ([Reanimated docs](https://docs.expo.dev/versions/v58.0.0/sdk/reanimated/)); both "Included in Expo Go". Skia's peers already require them ([npm](https://registry.npmjs.org/@shopify/react-native-skia/latest)).
- Worklets docs expose `createWorkletRuntime` (extra JS runtime on another thread) and `scheduleOnRuntime` (native only, not web) ([docs 0.10-0.12](https://docs.swmansion.com/react-native-worklets/docs/0.10-0.12/threading/scheduleOnRuntime/)). Note: the unversioned docs say scheduling from the UI runtime or another worker needs Bundle Mode ([search result](https://docs.swmansion.com/react-native-worklets/docs/threading/scheduleOnRuntime)); I did not open the 0.13 page itself, so check 0.13 behaviour (**UNVERIFIED**).
- `react-native-worklets-core` (Margelo) is a separate library, MIT, pushed 2026-04-22 ([API](https://api.github.com/repos/margelo/react-native-worklets-core)); only Filament needs it. Do not mix it with Reanimated's worklets.
- **Hermes WebAssembly: UNVERIFIED.** Evidence is conflicting: the official RN 0.84 post says Hermes V1 is default but does not mention WebAssembly ([blog](https://reactnative.dev/blog/2026/02/11/react-native-0.84)); Hermes's own Features doc has no WebAssembly entry ([Features.md](https://raw.githubusercontent.com/facebook/hermes/main/doc/Features.md)); a Callstack event page claims 0.84 adds "WebAssembly support" ([page](https://www.callstack.com/events/react-native-0-84-and-other-news)) but is a secondary source; Hermes issue [#429](https://github.com/facebook/hermes/issues/429) says Hermes lacked a `global.WebAssembly` (old). Action: run `typeof WebAssembly` on a RN 0.88 device build before relying on it.
- **Consequence**: write the physics in plain TypeScript (hard-sphere collisions in a box, simple Lennard-Jones) in typed arrays; that runs in a worklet or on the JS thread with no WASM. Rapier is not needed for chemistry boxes, and `rapier.js` is archived anyway ([repo](https://github.com/dimforge/rapier.js)).

### 4. Molecule viewers (reference only)
3Dmol.js (BSD-3), NGL (MIT), Mol* (MIT), Miew (MIT) are all browser WebGL/DOM libraries; reusing them in RN means a WebView, which we want to avoid. I did not find any of them documenting a React Native renderer (**UNVERIFIED**; absence of evidence). Use them only to compare how ball-and-stick, van der Waals and bond styles are conventionally drawn and coloured (CPK).

### 5. 3D coordinates
- **VSEPR ourselves (recommended)**: geometries are fixed unit-vector sets (linear, trigonal planar, tetrahedral, trigonal bipyramidal, octahedral, plus lone-pair variants: bent, pyramidal, see-saw, T-shaped, square planar, square pyramidal). A small TS table plus bond lengths gives every molecule the textbook needs, offline, no dependency, and is deterministic for the figure spec (like the existing JSON-driven figures).
- **RDKit.js**: BSD-3, but WASM-only per its description ([npm](https://registry.npmjs.org/@rdkit%2Frdkit/latest)); on-device blocked until Hermes WASM is confirmed. It could generate coordinates at build time and store them as JSON for larger organics.
- **OpenChemLib JS**: BSD-3, actively pushed; whether it is pure JS or WASM I did not verify (**UNVERIFIED**). Same build-time option.

## 6. Recommendation

One simulation core, two renderers:
- **Core (shared, renderer-free)**: TypeScript module holding particle state in `Float32Array`s (x, y, z, vx, vy, vz, species) with a fixed-step integrator, wall + pair collisions in a box, thermostat, and a molecule model (atoms, bonds, VSEPR coordinates). Positions are read out as a flat array each frame. 2D is the same code with z = 0. No WASM dependency.
- **2D renderer**: `@shopify/react-native-skia`, `Atlas` with one pre-rendered disc sprite per species and an `RSXform[]` updated per frame; drive time with a Reanimated/worklets frame callback so React never re-renders per frame. Keep `react-native-svg` for axes, labels and static figures. Web: Skia with CanvasKit (accept the download) or fall back to svg if the bundle cost is too high.
- **3D renderer**: keep three.js on `expo-gl` exactly as `native3d` does, adding an `InstancedMesh` (or Points impostors) for particles and atoms, cylinders for bonds, and the existing orbit `PanResponder` + SVG label overlay. Rotation of molecules is just camera orbit, which the engine already does.
- **Loop placement**: start on the JS thread with `requestAnimationFrame` (the engine's `rafDriver`) because expo-gl rendering is tied to the JS thread's GL context; move physics to a worklet runtime only if profiling shows JS-thread stalls. Skia + Reanimated can run the whole 2D loop on the UI thread.
- **Not now**: Filament, Babylon, WGPU, Unity/Godot, WebView viewers, Rapier, RDKit on device.

### Reuse from the BYE Math engine
- `ByeFigure3D` pattern: `GLView` + `createGLScene` + `render(camera, ms)` + PanResponder orbit + replay/auto-rotate state.
- `glRenderer.ts`'s `createRenderer` workaround for three >= r163 on expo-gl (essential), `Line2` thick lines, lighting rig, disposal list.
- `overlay3d` / `SceneSvg` for labels projected over the GL view (atom symbols, bond angles, charges).
- `useFigureClock`, `rafDriver`, `animationDriver` injection, `reduceMotion` handling, `FigureError` fallback, `ByeLightTheme` roles/colours, `frameAt` for timed overlays.
- Core camera maths (`eyeOf`, `FOV`, `NEAR`, `FAR`, `Camera {azimuth, elevation, zoom}`).
